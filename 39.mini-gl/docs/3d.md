# Implementación de MiniGL 3D — MiniGPU

## 1. Objetivo del proyecto

Implementar la primera versión funcional de **MiniGL 3D**, una API gráfica ligera para la arquitectura MiniGPU, utilizando C89 y un command buffer binario independiente del backend de renderizado.

El objetivo es disponer de una cadena completa:

```text
Aplicación / MiniProcessing
          |
          v
       MiniGL 3D
          |
          v
   Command Buffer
          |
    +-----+------+
    |            |
    v            v
Renderer       Renderer
software       MiniGPU
C89            SIMT
    |
    +--> PC host
    +--> MiniCPU FPGA
```

El renderer MiniGPU SIMT no se implementará en esta primera versión. Se diseñarán las interfaces para poder incorporarlo posteriormente.

La primera demostración será un **cubo 3D giratorio**, con perspectiva, clipping, Z-buffer y framebuffer RGB565 de 320×240 píxeles.

El proyecto debe aprovechar el código MiniGL 2D existente, manteniendo compatibilidad en la medida de lo posible y evitando duplicar infraestructuras.

## 2. Principios arquitectónicos obligatorios

1. Todo el código compartido debe ser compatible con **C89**.
2. MiniGL es una API de estado gráfico, recursos y generación de comandos. No rasteriza ni transforma vértices.
3. El command buffer es el contrato entre MiniGL y los renderizadores.
4. El command buffer no puede contener punteros nativos del PC.
5. Las direcciones de recursos son direcciones de 32 bits del espacio de RAM compartida de MiniGPU.
6. CPU y GPU comparten memoria SDRAM. No debe suponerse que existe coherencia automática entre cachés.
7. El renderer host y el renderer MiniCPU deben compartir exactamente el mismo núcleo C89.
8. El renderer software debe ser independiente de MiniGL y Processing.
9. Las etapas del renderer deben ser módulos separados, con interfaces claras.
10. No introducir buffers intermedios completos entre etapas salvo que sean necesarios.
11. Los recursos persistentes viven fuera del command buffer.
12. Cada frame debe ser autocontenido respecto al estado gráfico necesario para reproducirlo.
13. El sistema debe permitir sustituir en el futuro etapas software por hardware dedicado.
14. Priorizar simplicidad, claridad, portabilidad y capacidad de validación frente a optimizaciones prematuras.

## 3. Capas del sistema

### 3.1. MiniProcessing

Implementar una capa mínima inspirada en Processing, exclusivamente para demostrar el cubo.

Funciones necesarias:

```c
size(320, 240, P3D);
background(20);
translate(x, y, z);
rotateX(angle);
rotateY(angle);
fill(255, 140, 40);
noStroke();
box(100);
```

Además de `setup()` y `draw()` como estructura del ejemplo.

MiniProcessing debe ser una capa fina sobre MiniGL. Puede mantener una matriz de transformación local y una pila de matrices si resulta necesario, aunque la pila no es imprescindible para el primer cubo.

`translate()` y `rotateX/Y()` deben modificar la matriz local, no generar necesariamente comandos individuales.

`box()` debe utilizar una malla de 8 vértices y 36 índices (12 triángulos), y llamar a MiniGL para dibujarla.

La geometría del cubo debe crearse una sola vez y reutilizarse en los frames siguientes.

### 3.2. MiniGL 3D

Responsabilidades:

- Gestionar estado gráfico.
- Construir matrices mediante funciones auxiliares.
- Registrar recursos mediante handles.
- Resolver handles a direcciones de RAM compartida.
- Generar comandos binarios.
- Validar argumentos y capacidad del command buffer.
- Mantener el orden de las operaciones.
- No realizar transformación de vértices, clipping ni rasterización.

Proponer una API pública equivalente a:

```c
mgl_begin_frame();

mgl_clear(color, depth);

mgl_set_matrix(MGL_MATRIX_PROJECTION, &projection);
mgl_set_matrix(MGL_MATRIX_VIEW, &view);
mgl_set_matrix(MGL_MATRIX_MODEL, &model);

mgl_set_depth_test(1);
mgl_set_color(color);

mgl_draw_mesh(mesh);

mgl_end_frame();
```

La API exacta puede ajustarse para mantener compatibilidad con MiniGL 2D, pero debe conservar estas responsabilidades.

### 3.3. Renderer software C89

Implementar un renderer de referencia escalar, independiente de la arquitectura SIMT.

Debe consumir directamente el command buffer binario y acceder a los recursos mediante direcciones del espacio de memoria MiniGPU.

Debe funcionar en:

- PC host, usando RAM emulada.
- MiniCPU FPGA, usando RAM compartida real.

No deben existir dos implementaciones independientes del algoritmo de renderizado.

### 3.4. Renderer MiniGPU

No implementarlo todavía.

El futuro renderer SIMT deberá consumir el mismo contrato binario y los mismos recursos, aunque internamente pueda organizar el trabajo de manera diferente.

MiniGPU tiene 8 lanes por warp. No introducir esta organización en el renderer software de referencia.

## 4. Tipos y aritmética

Definir tipos propios y configurables.

Ejemplo conceptual:

```c
typedef float mgl_real_t;

typedef struct {
    mgl_real_t m[16];
} mgl_mat4_t;
```

Inicialmente utilizar `float32` y enteros normales.

La arquitectura MiniCPU dispone de multiplicación y división Q16.16 por hardware, mientras que `float` se implementa por software. MiniGPU también soporta `float32`, pero Q16.16 puede resultar más eficiente.

Por tanto:

- No fijar `float32` como único formato futuro.
- Preparar el código para una variante Q16.16.
- Centralizar las operaciones matemáticas en módulos especializados.
- No asumir que cambiar un `typedef` basta para implementar Q16.16.
- Separar los tipos utilizados para calcular de los formatos serializados.
- Verificar tamaños de los tipos enteros en cada plataforma.
- Evitar depender de que `unsigned long` mida exactamente 32 bits en PC.

Definir identificadores binarios para:

```c
MGL_FORMAT_FLOAT32
MGL_FORMAT_Q16_16
```

Inicialmente implementar las operaciones `float32`. Los formatos todavía no soportados deben rechazarse explícitamente.

## 5. Matrices

Utilizar tres matrices independientes:

```c
MGL_MATRIX_MODEL
MGL_MATRIX_VIEW
MGL_MATRIX_PROJECTION
```

Convención inicial:

- Matrices 4×4.
- Orden column-major.
- Vectores columna.
- Transformación `Projection × View × Model`.
- Ángulos en radianes.

Implementar funciones para:

- Identidad.
- Multiplicación.
- Traslación.
- Escalado.
- Rotación X.
- Rotación Y.
- Rotación Z.
- Perspectiva.
- Opcionalmente `look_at()`.

Documentar el orden de composición de las transformaciones para que `translate()` y `rotateY()` tengan un comportamiento consistente.

## 6. Command buffer binario

Mantener el diseño existente de MiniGL basado en una cabecera general de 16 bytes y comandos con cabecera común de 16 bytes.

### 6.1. Cabecera general

```c
typedef struct {
    mgl_u32 magic;
    mgl_u32 version;
    mgl_u32 used_bytes;
    mgl_u32 capacity;
} mgl_buffer_header_t;
```

Usar un magic identificable, por ejemplo `MGLC`, y una versión nueva compatible con la evolución 3D.

Definir explícitamente el orden de bytes, la alineación y las reglas de serialización.

No depender del padding accidental de estructuras C.

### 6.2. Cabecera de comando

```c
typedef struct {
    mgl_u16 opcode;
    mgl_u16 flags;
    mgl_u32 size_bytes;
    mgl_u32 arg0;
    mgl_u32 arg1;
} mgl_cmd_t;
```

Tamaño binario: 16 bytes.

Los comandos pueden contener payload adicional inmediatamente después de esta cabecera.

Los comandos deben poder recorrerse mediante `size_bytes`, validando sus límites.

### 6.3. Comandos necesarios

Implementar inicialmente:

```text
SET_RENDER_TARGET
CLEAR
SET_VIEWPORT
SET_MATRIX
SET_RENDER_STATE
SET_COLOR
DRAW_INDEXED
END_FRAME
```

Mantener los comandos 2D existentes y permitir intercalar operaciones 2D y 3D respetando el orden.

No crear opcodes públicos para `TRANSFORM_VERTEX`, `CLIP_TRIANGLE` o `BOX`.

### 6.4. SET_MATRIX

Se ha decidido utilizar un único opcode `SET_MATRIX`, no tres opcodes distintos.

Formato:

```text
opcode       = MGL_CMD_SET_MATRIX
flags        = 0
size_bytes   = 80
arg0         = MODEL / VIEW / PROJECTION
arg1         = FLOAT32 / Q16_16
payload      = 16 componentes de 32 bits
```

Tamaño total: 80 bytes.

La matriz debe copiarse por valor al command buffer. No se permite guardar referencias a matrices temporales de la aplicación.

### 6.5. DRAW_INDEXED

Debe contener, como mínimo:

```text
vertex_addr
index_addr
vertex_count
index_count
vertex_format
index_format
vertex_stride
```

Las direcciones son direcciones de 32 bits de RAM compartida.

El comando no debe contener handles de aplicación ni punteros nativos.

El formato exacto y el tamaño final deben definirse explícitamente, con alineación adecuada y tests binarios.

### 6.6. Formatos de vértices

Inicialmente:

```text
POSITION_F32_XYZ
INDEX_UINT16
```

Reservar identificadores para:

```text
POSITION_Q16_16_XYZ
INDEX_UINT32
```

Incluir stride explícito para poder ampliar los formatos en el futuro.

No fijar para siempre una única estructura de vértice.

### 6.7. Estado gráfico

Para el primer cubo:

- Color uniforme RGB565.
- Depth test habilitado.
- Depth write habilitado.
- Blending deshabilitado.
- Culling deshabilitado inicialmente.
- Viewport configurable.
- Proyección perspectiva.

El renderer debe partir de un estado inicial definido para cada ejecución.

MiniGL puede evitar emitir estados redundantes dentro de un frame, pero no debe depender de estados ocultos de frames anteriores.

## 7. Recursos y ciclo de vida

Adoptar el modelo híbrido inspirado en APIs gráficas modernas.

### 7.1. Handles en la API

La aplicación utiliza handles para identificar recursos.

Por ejemplo:

```c
mesh = mgl_create_mesh(...);
mgl_draw_mesh(mesh);
```

MiniGL mantiene los metadatos y resuelve el handle al construir el command buffer.

### 7.2. Direcciones en los comandos

Los comandos contienen direcciones de RAM compartida, no handles.

Esto permite que el renderer host, MiniCPU y MiniGPU consuman los mismos comandos sin necesitar una tabla de handles de MiniGL.

### 7.3. Propiedad de memoria

Permitir dos modelos:

- Recursos cuya memoria administra MiniGL.
- Recursos que utilizan memoria SDRAM proporcionada por la aplicación.

El segundo modelo es importante para aplicaciones existentes que gestionan sus propios buffers, imágenes o fuentes.

No imponer copias innecesarias.

### 7.4. Vida útil

Un recurso referenciado por un command buffer debe permanecer válido y sin modificaciones incompatibles hasta finalizar su ejecución.

La aplicación no debe sobrescribir vértices mientras el renderer todavía los utiliza.

Para la primera versión, el renderer host será síncrono.

Diseñar las interfaces para permitir posteriormente:

- Ejecución asíncrona.
- Fences de finalización.
- Varios frames en vuelo.
- Reutilización segura de buffers.

No implementar todavía un sistema complejo de seguimiento automático de dependencias.

## 8. Memoria compartida y emulación host

La CPU y GPU de MiniGPU comparten SDRAM.

En el host, representar esa memoria mediante un array o región de memoria emulada.

El command buffer y los recursos deben utilizar las mismas direcciones lógicas en ambas plataformas.

El renderer host debe resolver las direcciones a posiciones dentro de la RAM emulada.

MiniCPU debe poder utilizar un adaptador de acceso a memoria real.

Separar el acceso a memoria del núcleo del renderer.

Evitar callbacks indirectos por cada píxel cuando perjudiquen el rendimiento. Permitir accesos eficientes al framebuffer y Z-buffer.

Validar rangos y alineaciones en el host.

No suponer coherencia automática de cachés entre CPU y GPU; documentar la necesidad futura de operaciones de visibilidad y sincronización.

## 9. Renderer software modular

Separar las siguientes etapas:

```text
commands.c
state.c
transform.c
clipping.c
viewport.c
raster3d.c
raster2d.c
fragment.c
math.c
memory.c
```

### Decodificación

Interpretar opcodes y actualizar el estado.

Validar tamaños y direcciones.

### Transformación

Leer vértices y aplicar Model, View y Projection.

Conservar coordenadas homogéneas hasta completar el clipping.

### Clipping

Recortar correctamente los triángulos contra el volumen de visión.

Incluir recorte del plano cercano.

No limitarse a descartar triángulos que crucen el near plane.

### Viewport

Realizar división perspectiva y conversión a coordenadas de pantalla.

### Rasterización

Rasterizar triángulos mediante un algoritmo escalar determinista.

Utilizar enteros o punto fijo para cobertura cuando resulte conveniente.

### Fragmentos

Aplicar:

- Depth test.
- Depth write.
- Escritura RGB565.
- Blending cuando se incorpore.

### Flujo de ejecución

Procesar cada triángulo de principio a fin, sin almacenar obligatoriamente una lista completa de triángulos transformados.

Ejemplo conceptual:

```c
for (i = 0; i < index_count; i += 3) {
    fetch_triangle(...);
    transform_triangle(...);
    clip_triangle(...);
    project_and_rasterize(...);
}
```

El clipping puede producir varios triángulos a partir de uno.

Evitar asignaciones dinámicas dentro del bucle de rasterización.

## 10. Posible aceleración hardware futura

Las etapas deben tener interfaces suficientemente claras para permitir sustituir su implementación por hardware.

Candidatas:

- Transformación de vértices.
- Proyección.
- Rasterización.
- Depth test.
- Blending.

No implementar hardware ahora.

No introducir FIFOs, MMIO ni protocolos físicos prematuramente.

La separación modular es lógica: una etapa puede convertirse posteriormente en una unidad hardware alimentada por lotes de trabajo.

El renderer software C89 debe seguir existiendo como referencia funcional completa.

## 11. Ejemplo del cubo

Implementar un ejemplo equivalente a:

```c
float angle = 0.0f;

void setup(void)
{
    size(320, 240, P3D);
}

void draw(void)
{
    background(20);

    translate(160, 120, 0);
    rotateX(angle * 0.6f);
    rotateY(angle);

    fill(255, 140, 40);
    noStroke();

    box(100);

    angle += 0.02f;
}
```

Adaptar la configuración de cámara y la semántica de coordenadas de Processing para que el cubo se visualice correctamente con perspectiva.

La malla debe contener 8 vértices y 36 índices.

La geometría se crea una sola vez. La matriz del modelo cambia en cada frame.

## 12. Command buffer esperado del cubo

```text
HEADER

SET_RENDER_TARGET
    framebuffer_addr
    depthbuffer_addr
    width  = 320
    height = 240

CLEAR
    color = RGB565(20,20,20)
    depth = valor lejano

SET_VIEWPORT
    x = 0
    y = 0
    width = 320
    height = 240

SET_MATRIX PROJECTION FLOAT32
    16 valores

SET_MATRIX VIEW FLOAT32
    16 valores

SET_MATRIX MODEL FLOAT32
    16 valores

SET_RENDER_STATE
    depth_test  = enabled
    depth_write = enabled
    blending    = disabled
    culling     = disabled

SET_COLOR
    RGB565(255,140,40)

DRAW_INDEXED
    vertex_addr
    index_addr
    vertex_count = 8
    index_count  = 36
    vertex_format = POSITION_F32_XYZ
    index_format  = UINT16

END_FRAME
```

La cámara, proyección y otros estados pueden reutilizarse dentro de un frame, pero cada frame debe ser reproducible independientemente.

## 14. Validación

Implementar pruebas para:

1. Tamaños y codificación de cabeceras.
2. Serialización y decodificación de `SET_MATRIX`.
3. Serialización y decodificación de `DRAW_INDEXED`.
4. Formatos numéricos admitidos y rechazados.
5. Resolución de handles a direcciones.
6. Límites y capacidad del command buffer.
7. Multiplicación y composición de matrices.
8. Transformación de vértices.
9. Clipping contra el plano cercano.
10. Rasterización y reglas de cobertura.
11. Depth test.
12. Reproducción de command buffers guardados.
13. Renderizado del cubo en diferentes ángulos.

El renderer host debe poder generar archivos PPM a partir del framebuffer RGB565.

No utilizar SDL, OpenGL ni otra biblioteca gráfica para rasterizar.

Si se utiliza una biblioteca para mostrar imágenes en una ventana, debe quedar fuera del renderer.

## 15. Orden de implementación

### Fase A — MiniGL 3D

Implementar:

- Tipos y configuración.
- Matemáticas.
- Recursos y handles.
- Comandos 3D.
- Serialización.
- Tests binarios.

No depender del renderer para validar esta fase.

### Fase B — Renderer host

Implementar:

- Memoria emulada.
- Decodificador.
- Transformación.
- Clipping.
- Viewport.
- Rasterización.
- Z-buffer.
- Salida PPM.

### Fase C — MiniProcessing

Implementar únicamente las primitivas utilizadas por el cubo.

### Fase D — Integración

Ejecutar el cubo giratorio de extremo a extremo.

Generar varios frames y comprobar visualmente el resultado.

### Fase E — Preparación MiniCPU

Comprobar compatibilidad C89, ausencia de dependencias del host, uso de memoria y portabilidad de tipos.

No realizar todavía una optimización completa Q16.16.

## 17. Restricciones finales

No introducir shaders programables, texturas, iluminación compleja, múltiples colas GPU ni gestión automática avanzada de recursos en esta primera versión.

No rediseñar MiniGL 2D desde cero.

No utilizar punteros nativos dentro del command buffer.

No mezclar la implementación del renderer con MiniGL.

No acoplar el renderer host a la organización SIMT de MiniGPU.

No fijar `float32` como única representación numérica futura.

No añadir optimizaciones que compliquen innecesariamente la referencia software.

**Prioridad fundamental:** obtener un primer sistema 3D correcto, modular, portable y verificable, que permita evolucionar progresivamente desde el renderer C89 hasta MiniGPU y posibles aceleradores hardware.

Antes de modificar código existente, inspeccionar el repositorio y su documentación. Identificar qué partes ya están implementadas, cuáles pueden reutilizarse y cuáles requieren cambios. Mantener compatibilidad cuando sea posible y documentar cualquier cambio del contrato binario.

Si alguna decisión no está completamente especificada, elegir la solución más sencilla compatible con los principios anteriores y documentarla, en lugar de ampliar innecesariamente el alcance.
